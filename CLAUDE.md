# Customer Churn Prediction Platform

## What this project is
A web app where a user uploads customer data (one row per customer) and gets back
who is likely to churn, why, and what retention action to take. If the file has a
churn column, the platform trains and compares models; if not, it scores the file
with an already-trained model. Solo portfolio project, built in small steps, paced
for learning. A person always approves a model before it becomes champion.

## Architecture at a glance
Two paths, three stores. Nothing below is built yet; this is the target shape.
1. **Training path (background job):** ingest and validate → clean → engineer
   features → train and tune several models → compare → register one champion.
2. **Serving path (on request):** load the champion → score → explain → recommend.
3. **Stores:** SQLite (metadata, predictions), local disk (raw files, model files),
   MLflow (runs and the champion model).

Full detail lives in `project-notes/PLAN.md` and `GUIDE.md` (git-ignored, so they
exist only on the author's machine).

## How we work (read before changing anything)
- **The user drives, Claude advises.** One small step at a time, then stop and wait.
  Ask before each phase and before each step. Never write several files at once
  without a go-ahead, and never add extra scope unasked (suggest it instead).
- **The user chooses every tool and design.** Before a non-trivial choice (library,
  model, storage, structure), give a decision card: the decision, a recommendation
  with its main downside, the realistic alternatives, the cost of changing later,
  and a question. Wait for the answer. Install or create nothing until approved.
- **Record the choice** in `DECISIONS.md` once made: options worth considering, what
  was chosen, and why.
- **Build the thin path first.** Follow the phases in `project-notes/PLAN.md`; each
  ends at a gate. Do not start work from a later phase early.
- **Explain before writing.** This is a learning project: say what a step does and
  why in plain language before any code. After each file, give short revision notes
  in chat (imports, data structures with example values, functions, key idea, two or
  three self-check questions without answers).
- **Be honest.** If a choice looks like a poor fit, say so once, then follow the
  user's decision. If unsure of a version or an API, check instead of guessing.
- **Do not tune off a single run.** One surprising metric, flaky test or odd result
  needs a second data point before it is called a bug or a fix.
- **Version control:** the folder is not a git repository yet. Once it is, use a
  branch + PR for every change, with a real description, even when solo.

## Code conventions
- PEP 8: `snake_case` for functions, variables, modules and files; `PascalCase` for
  classes; `UPPER_SNAKE_CASE` for constants; leading underscore for private helpers.
- Lines up to 88 characters. Type hints and docstrings on public functions.
- Small, single-purpose functions. Comment the why, not the what.
- Every piece of logic gets a test, written as it is built.
- Dependencies go in `pyproject.toml` via `uv add`. No `requirements.txt`.
- Fixed random seeds anywhere randomness affects results, so runs reproduce.

## ML rules that must not be broken
These protect the validity of every result, so they apply to all code that touches
data or models.
- **Fit on train only.** Scalers, encoders and imputers are fitted on training data
  and reused unchanged at prediction time (one pipeline object for both).
- **No leakage.** Features use only data from before the snapshot date; the label
  comes only from the window after it. Columns that predict the target almost
  perfectly (cancellation date, reason for leaving) are flagged and excluded.
- **Split by time** when the data has dates (train on older, test on the newest);
  fall back to a stratified random split only when it does not, and say so visibly.
- **Judge by PR-AUC, not accuracy**, because churn is imbalanced. Also report
  ROC-AUC, recall in the top 10% of risk, and Brier score.
- **Beat the baseline.** A model becomes champion only if it beats the majority-class
  and logistic-regression baselines by a margin agreed beforehand.
- **Set the decision threshold from the retention budget**, not at 0.5.
- **Run the tests (and the evaluation, once it exists) before committing** a change
  to features, preprocessing or modelling.

## Data rules
- Synthetic data or public datasets only. No real customer data or real PII enters
  this repo, ever.
- Datasets are never committed. Fetch public ones with a script in `scripts/`, and
  check each dataset's license before using or bundling it.
- Thresholds and rules that depend on the data (e.g. minimum rows, risk bands) are
  tuned against the actual data's numbers, not picked abstractly. Re-check them
  after regenerating or swapping a dataset.
- Failed uploads get a plain-language reason and a suggested fix, never a stack trace.
